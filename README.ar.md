# HealTrip — مساعد قرار المريض بالذكاء الاصطناعي (نموذج أولي)

**[English version ← README.md](README.md)**

> ## 🔗 العرض الحي: **https://healtrip-demo.vercel.app**
> جرّب: *"عندي ألم في الصدر ومحتار هل أروح طبيب قلب ولا الطوارئ ولا آخذ رأي ثاني"*. عندما يسأل الاستقبال، استخدم ملف المريض الخيالي **`MRN-100001`** وتاريخ الميلاد **12/04/1971**، أو قل إنه ليس لديك ملف. زر اللغة في الأعلى.

> ⚠️ **نموذج أولي. بيانات وهمية فقط. ليس نصيحة طبية. ليس نظام تشخيص. لا يدّعي التوافق مع HIPAA أو الأنظمة السعودية.** جميع الأطباء والمستشفيات والمواعيد والمرضى خياليون.

## 1. نظرة عامة

يكتب المريض بالعربية أو الإنجليزية:

> *"عندي ألم في الصدر ومحتار هل أروح طبيب قلب ولا الطوارئ ولا آخذ رأي ثاني."*

المساعد **لا** يجيب مباشرة بـ"راجع طبيب قلب". بل:

1. يفحص علامات الطوارئ **أولًا**.
2. يسأل فقط الأسئلة القليلة التي تؤثر في هذا القرار.
3. يترك **طبقة فرز حتمية** (كود، وليس النموذج اللغوي) تختار مسار الرعاية: طوارئ، عاجل، طبيب مختص، رعاية أولية، أو رأي ثانٍ.
4. فقط إذا سمح المسار بذلك، يستدعي أدوات تبحث في قاعدة بيانات حقيقية لمقدمي الخدمة.
5. يعرض خيارات موجودة فعلًا في قاعدة البيانات، ولا شيء غيرها.

**المساعد يوجّه ولا يشخّص.** لا يذكر اسم مرض ("يبدو أنها ذبحة")، ولا يخمّن السبب، ولا يقترح دواء. مخرجه الوحيد هو *نوع الرعاية المناسبة* و*الأطباء الحقيقيون الذين يمكنهم رؤيتك*. التشخيص للطبيب فقط.

تصف HealTrip نموذجها بأنه **Decision-First Healthcare**: القرار الطبي الصحيح يأتي قبل الحجز. هذا النموذج الأولي مبني على هذه الفكرة: *قرّر بأمان، ثم ابحث عن مقدم الخدمة.*

المبدأ الهندسي في كل المشروع:

> **النموذج اللغوي يفهم ويتحدث. الكود يقرر ما هو آمن. قاعدة البيانات تقرر ما هو صحيح.**

## سير عمل المريض (كما يعمل استقبال المستشفى)

يتبع المساعد نفس مسار مكتب الاستقبال في مستشفى حقيقي، مع فحص السلامة قبل أي إجراءات إدارية:

</div>

```
 ┌──────────────────────────────────────────────────────────────────────────────────────────┐
 │ EVERY message: red-flag check (code). "I can't breathe" / "أغمي علي" → emergency now,     │
 │ fixed message + nearest ER hospitals. No reception, no questions, no booking.             │
 └──────────────────────────────────────────────────────────────────────────────────────────┘
   1  SAFETY FIRST     "Is the chest pain happening right now?"
   2  RECEPTION        "Do you have a patient file with us?" → date of birth → verified in code
   3  TRIAGE           only the questions that can still change the decision; rules pick the clinic
   4  HANDOFF          "I'm transferring you to the Cardiology clinic assistant." + summary → "Is this correct?"
   5  CONFIRM          yes → continue · no → "What should I correct?"
   6  DOCTORS + OFFERS matching doctors from the DB + optional services (cross-sell / upsell)
   7  SCHEDULE         real open times → patient taps Confirm (the AI cannot book)
   8  TICKET           DB-generated ticket HT-2026-000123 → doctor e-mail + hospital-system message (mocked)
```

<div dir="rtl">

| الخطوة | ماذا يحدث |
|---|---|
| **1. السلامة أولًا** | *"هل ألم الصدر موجود الآن؟"*، ويُسأل **قبل** رقم الملف: لا أحد يعاني ألمًا نشطًا في الصدر يجب أن يبحث عن أوراقه. |
| **2. الاستقبال** | *"هل لديك ملف طبي لدينا؟ رقم الملف أو الهوية؟"* ← *"ما تاريخ ميلادك؟"* ← يتم التحقق بالكود ← *"شكرًا السيد أحمد، وجدت ملفك."* (بدون ملف أو بعد 3 محاولات فاشلة ← يكمل كزائر) |
| **3. الفرز** | فقط الأسئلة التي ما زالت قادرة على تغيير القرار، والقواعد تختار العيادة. |
| **4. التحويل** | *"سأحوّلك الآن إلى مساعد عيادة أمراض القلب."* ثم ملخص من الملف ومن إجابات اليوم، و*"هل هذه المعلومات صحيحة؟"* (قالب يُملأ من قاعدة البيانات، والنموذج اللغوي لا يعيد صياغة الملف الطبي أبدًا) |
| **5. التأكيد** | إذا قال المريض نعم يكمل، وإذا قال لا: *"ما الذي يجب تصحيحه؟"* |
| **6. الأطباء والعروض** | أطباء مطابقون من قاعدة البيانات، وخدمات اختيارية (بيع متقاطع وترقية) تظهر الآن فقط. |
| **7. الموعد** | مواعيد متاحة حقيقية، والمريض يضغط «تأكيد» (الذكاء الاصطناعي لا يستطيع الحجز). |
| **8. التذكرة** | رقم تذكرة تولّده قاعدة البيانات، ثم إشعار للطبيب بالبريد ولنظام المستشفى (تجريبي). |

### سير العمل بالصور

تشغيل حقيقي لواجهة العرض (Next.js) مع الخادم الحقيقي ونموذج لغوي حي (DeepSeek). ملف المريض `MRN-100001` وجميع الأطباء خياليون.

**1 · السلامة أولًا، ثم الاستقبال والتحقق من الهوية**

![الاستقبال: سؤال الألم الآن، رقم الملف، تاريخ الميلاد، العثور على الملف](docs/screenshots/01-reception-file-lookup.jpg)

> السؤال الأول هو *"هل ألم الصدر موجود الآن؟"*، **قبل** أي إجراء إداري. بعدها فقط يطلب الاستقبال رقم الملف ثم تاريخ الميلاد. لا يُعثر على الملف إلا إذا تطابق الاثنان: *"شكرًا السيد أحمد، وجدت ملفك."* وهذه الجملة نص ثابت وليست من إنتاج النموذج. تحت كل رد يوجد سطر **"كيف تم إنتاج هذا الرد"** يُظهر القاعدة التي عملت (`Q_PAIN_NOW`، `Q_ASSOCIATED`…)، وبفتحه يظهر المسار الكامل: الحقائق المستخرجة ← القاعدة ← الأدوات.

**2 · التحويل إلى مساعد العيادة الذي يعيد الملخص ويطلب التأكيد**

![التحويل إلى مساعد عيادة القلب مع ملخص من الملف وإجابات اليوم](docs/screenshots/02-handoff-clinic-assistant.jpg)

> القواعد اختارت العيادة (`S_CARDIOLOGY`)، والواجهة تُظهر سطر التحويل. الملخص (الحالات المسجلة، الحساسية، آخر زيارة، إجابات اليوم) هو **قالب يُملأ من قاعدة البيانات والحقائق المنظّمة**. النموذج اللغوي لا يعيد كتابة السجل الطبي أبدًا، لأن إعادة الصياغة هي بالضبط المكان الذي تُخترع فيه حالة مرضية أو تسقط. لا يُعرض أي شيء قبل أن يؤكد المريض.

**3 · أطباء من قاعدة البيانات، ثم خدمات اختيارية**

![بطاقة طبيب من قاعدة البيانات وباقة فحص قلب اختيارية](docs/screenshots/03-doctors-and-offers.jpg)

> النموذج يشير إلى الأطباء بالمعرّف فقط (`[DOC-001]`)، والواجهة تستبدله بالاسم **من بطاقة قاعدة البيانات في نفس الاستجابة**، والبطاقة نفسها صف من قاعدة البيانات. العرض (بيع متقاطع) يأتي من جدول `offers`، ويظهر فقط بعد التأكيد، وعروض السفر مخفية لأن هذا الطبيب في الرياض.

**4 · مواعيد حقيقية ← المريض يؤكد ← تذكرة من قاعدة البيانات**

![مواعيد متاحة، أحدها محجوز، والتذكرة HT-2026-000001](docs/screenshots/04-booking-ticket.jpg)

> المواعيد صفوف حقيقية من جدول `slots`. الضغط على **«تأكيد»** يستدعي `POST /bookings` (النموذج لا يملك أداة حجز). رقم التذكرة `HT-2026-000001` يولّده تسلسل Postgres، ويتم إشعار الطبيب (بريد) ونظام المستشفى (FHIR `Appointment`) عبر صندوق الصادر (تجريبي).

**5 · العربية، من اليمين إلى اليسار، حالة طوارئ**

![واجهة عربية: "عندي ألم في صدري وما أقدر أتنفس" ← رسالة طوارئ ثابتة مع 997](docs/screenshots/05-arabic-emergency.jpg)

> جملة *"عندي ألم في صدري وما أقدر أتنفس"* تُفعّل قاعدة العلامة الحمراء `RF_BREATHING` على النص الخام. **النموذج اللغوي لا يُستدعى إطلاقًا**: الرد هو رسالة الطوارئ الثابتة المراجَعة مع 997 / 911، وتبقى الجلسة مقفلة على وضع الطوارئ (لا استقبال، لا بحث عن طبيب، لا حجز).

لماذا كل خطوة في مكانها:
- **السلامة قبل الهوية.** كشف الطوارئ يعمل على كل رسالة، وسؤال "هل الألم موجود الآن؟" يأتي قبل رقم الملف.
- **الهوية يتم التحقق منها ولا تُفترض.** رقم الملف وحده لا يكفي، يجب أن يطابق تاريخ الميلاد. عند الفشل تقول الرسالة "لم أتمكن من التحقق من هذه البيانات" ولا تكشف أبدًا هل الملف موجود. بعد 3 محاولات فاشلة يكمل المريض كزائر، وتُحذف المعرّفات من الجلسة بعد التحقق. (في الإنتاج: نفاذ / رمز تحقق OTP.)
- **مساعد العيادة يعيد الملخص ويطلب التأكيد** قبل عرض أي شيء، حتى يكتشف المريض أي معلومة فُهمت خطأ، بدل أن تُكتشف في العيادة.
- **البيع يحدث فقط بعد قرار مؤكد وغير عاجل.** لا يظهر أبدًا في مسارات الطوارئ، ولا يؤثر أبدًا في اختيار العيادة.

> **ملاحظة تصميم للإنتاج: وكلاء منفصلون ومنسّق واحد.** في الإنتاج يكون **الاستقبال** و**مساعد كل عيادة** (القلب، العظام…) وكلاء منفصلين، لكل منهم تعليماته وأدواته وصلاحياته. ومنسّق رئيسي يستدعيهم ويسلّمهم المحادثة:

</div>

```
                       ┌──────────────────────────┐
  patient ───────────▶ │ Main orchestrator        │  safety check on every message
                       └──────────┬───────────────┘
             calls ┌──────────────┴───────────────┐ calls
                   ▼                              ▼
  ┌────────────────────────────┐   ┌──────────────────────────────────────┐
  │ Reception agent            │   │ Clinic assistant agent (per clinic)  │
  │ tools: lookup_patient,     │   │ tools: search_providers, slots,      │
  │        verify_identity     │   │        offers, booking               │
  │ sees: identity data only   │   │ sees: verified file summary + facts  │
  └────────────────────────────┘   └──────────────────────────────────────┘
```

<div dir="rtl">

> لماذا الفصل: كل وكيل يحصل على **أقل صلاحية ممكنة** (الاستقبال لا يستطيع الحجز، ومساعد العيادة لا يرى أرقام الهوية الخام)، وتعليمات أصغر وأكثر تركيزًا، ويمكن اختبار كل وكيل وتعديله وحده. إضافة عيادة جديدة تصبح إضافة وكيل، وليس تضخيم تعليمات واحدة.
>
> **في هذا العرض التجريبي لم يتم فصلهم عمدًا.** منسّق واحد يؤدي الدورين وينتقل بينهما حسب `stage` (`reception → triage → confirm → recommend`)، والـAPI يُرجع `agent: "reception" | "clinic_assistant"` حتى تُظهر الواجهة التحويل. المطلوب كان نموذجًا أوليًا صغيرًا بوكيل واحد، وحدود المراحل في `backend/app/agent.py` هي المكان الذي سيحدث فيه الفصل.

### ملاحظات هندسية: ماذا كشف الاختبار الحي

تم اختبار كل شيء أولًا بنموذج لغوي وهمي مبرمج (مجاني، ثابت النتائج، وحالات الفشل متاحة عند الطلب). ثم تم تشغيل المسار الكامل مع نموذج حقيقي. النموذج الحقيقي كشف مشاكل لم يستطع الوهمي كشفها، و**كل إصلاح دخل في الكود مع اختبار يمنع رجوع المشكلة**:

| ما ظهر في التشغيل الحي | لماذا حدث | الإصلاح (كود، وليس تعليمات) |
|---|---|---|
| النموذج قال لمريض ألم صدر *"هذه ليست حالة طارئة ولا تحتاج الطوارئ"* | القواعد اختارت "طبيب مختص"، لكن النموذج أضاف طمأنة من عنده | فحص المخرجات يمنع الآن الطمأنة الكاذبة (بالعربية والإنجليزية: *"وليس الطوارئ"*، *"not an emergency"*…) ويستبدل الرد بنص ثابت |
| سؤالنا نحن *"هل لديك تشخيص سابق؟"* تم حظره | مرشّح منع التشخيص حظر كلمة "تشخيص" نفسها | يُحظر *ذكر* تشخيص وليس *السؤال* عنه، واختبار يتأكد أن أيًّا من أسئلتنا الثابتة لا يُحظر أبدًا |
| مريض لديه تشخيص في صمام القلب (بدون ألم صدر) سُئل "ما مشكلتك؟" 3 مرات ثم حُوّل لطبيب أسرة | القواعد كانت تعرف فقط: ألم صدر ← غير ذلك | قاعدة جديدة `S_REVIEW_OTHER`: التشخيص الذي يحتاج مراجعة هو مسار مستقل (رأي ثانٍ في ذلك التخصص) |
| *"لا ما عندي تشخيص"* لم تُسجَّل أحيانًا فتكرر نفس السؤال | حتى مع temperature 0 كان النموذج أحيانًا يُسقط حقلًا (لوحظ تقريبًا مرة من كل 5 في عينة صغيرة) | إذا كانت القواعد ستسأل نفس السؤال مرتين، يتم استخراج **مركّز** على ذلك السؤال وإجابته فقط |
| رغم التعليمة *"لا تشكر المريض"*، كتب النموذج *"شكرًا، تم التحقق"* بعد جملتنا الثابتة *"وجدت ملفك"* | التعليمات في الـprompt ليست ضمانًا | بعد جملة ثابتة، يكون السؤال التالي نصًّا ثابتًا ولا يُسأل النموذج أصلًا |
| DeepSeek قد يُرجع ردودًا فارغة | "يفكر" افتراضيًا وقد يستهلك كل الرموز في تفكير مخفي | `LLM_DISABLE_THINKING=true` |

القاعدة العامة: **ما يهم يُفرض بالكود ويُثبَّت باختبار، والتعليمات تشكّل الأسلوب فقط.**

**التكلفة المقاسة** (DeepSeek `deepseek-flash`، عدد الرموز من الـAPI، بأسعار وقت الذروة): محادثة كاملة من 6 رسائل استهلكت 14 استدعاء و11,519 رمزًا، أي تقريبًا **0.0045 دولار**.

## 3. تصميم الوكيل الذكي: من المسؤول عن ماذا

| المسؤولية | المسؤول | السبب |
|---|---|---|
| فهم كلام المريض (عربي/إنجليزي، لهجات) | **النموذج اللغوي** | اللغة هي ما يجيده النموذج |
| استخراج الحقائق المنظّمة (`PatientFacts`) | **النموذج اللغوي**، مع تحقق من المخطط | يحوّل النص الحر إلى حقول يمكن للكود أن يستنتج منها |
| تحديد السؤال التالي | **طبقة الفرز** تحدد *ما الناقص*، و**النموذج** يصيغه | الأهمية تقررها القواعد، والصياغة يقررها النموذج |
| اختيار مسار الرعاية (طوارئ / عاجل / مختص / أولية / رأي ثانٍ) | **كود حتمي** | قرار حرج للسلامة: يجب أن يكون قابلًا للاختبار ومتكررًا، وليس درجة ثقة من النموذج |
| أي الأدوات مسموح استدعاؤها | **بوابة الأدوات (كود)** | مثلًا: في الطوارئ لا بحث عن أطباء، فقط مستشفيات فيها طوارئ |
| معلومات مقدمي الخدمة (الأسماء، المستشفيات، اللغات، الرسوم) | **قاعدة البيانات عبر الأدوات** | النموذج لا يملك معرفة موثوقة بمقدمي الخدمة |
| الجملة النهائية التي يقرؤها المريض | **النموذج**، ثم **فحصان بالكود**: التأسيس على البيانات + منع التشخيص | لغة طبيعية، لكن فقط عن بيانات مُرجعة، وبدون تشخيص أو نصيحة علاجية أبدًا |

</div>

## 4. استدعاء الأدوات

| الأداة | المدخلات | المخرجات | متى يُسمح بها |
|---|---|---|---|
| `search_providers` | `city?`، `country?`، `language?`، `remote?` (التخصص والرأي الثاني **تحددهما القواعد** وليس النموذج) | قائمة أطباء من قاعدة البيانات | مسار مختص أو رعاية أولية أو رأي ثانٍ |
| `get_doctor_details` | `doctor_id` | بيانات الطبيب الكاملة مع المستشفى | طبيب أُرجع سابقًا في هذه المحادثة |
| `get_available_slots` | `doctor_id`، `mode?` | حتى 5 مواعيد متاحة بالتوقيت المحلي | طبيب أُرجع سابقًا في هذه المحادثة |
| `get_hospital_details` | `hospital_id` | بيانات المستشفى الكاملة | مستشفيات الأطباء المُرجَعين في هذه المحادثة |

**بوابة الأدوات** (`backend/app/tools.py`) تقف بين النموذج وقاعدة البيانات:
- `search_providers` مرفوض في مسارات الطوارئ والعاجل.
- `specialty` و`second_opinion` **تحددهما قواعد الفرز ولا يستطيع النموذج تغييرهما**. النموذج يختار فقط فلاتر المدينة والدولة واللغة.
- التفاصيل والمواعيد متاحة فقط لأطباء أُرجعوا في هذه المحادثة.

عميل النموذج (`backend/app/llm.py`) يستخدم صيغة OpenAI المتوافقة، لذا فإن DeepSeek (المستخدم في التشغيل الحي) أو Anthropic أو Groq أو Gemini أو OpenAI مجرد تغيير في `.env` وليس في الكود. مدخلات الأدوات يتم التحقق منها بـPydantic **قبل** أي استعلام.

## 5. السلامة

طبقتان، وكلاهما كود:

1. **فحص العلامات الحمراء** على الرسالة الخام (قواعد عبارات بالعربية والإنجليزية). يعمل **قبل** النموذج، فيستمر في الحماية حتى لو تعطلت خدمة الذكاء الاصطناعي.
2. **قواعد الفرز** على الحقائق المنظّمة. تتبع الاتجاه المحافظ في [إرشادات AHA/ACC لألم الصدر 2021](https://professional.heart.org/en/science-news/2021-guideline-for-the-evaluation-and-diagnosis-of-chest-pain/top-things-to-know)، والتي تنص على أن ألم الصدر **الحاد** يُعامل كحالة طارئة (اتصل بالإسعاف) وليس كحجز عيادة:
   - ألم صدر **موجود الآن أو بدأ حديثًا** ← **طوارئ**، حتى بدون أعراض أخرى
   - ألم صدر + ضيق تنفس / إغماء / تعرق / ألم ينتشر للذراع أو الفك أو الظهر ← **طوارئ**
   - ألم سابق أو متكرر بدون علامات خطر ← **طبيب مختص** (قلب)
   - تشخيص أو خطة علاج سابقة يريد المريض مراجعتها ← **رأي ثانٍ**

في الطوارئ **يتوقف البحث عن مقدمي الخدمة**، والرد رسالة ثابتة مراجَعة (ليست من النموذج):

> "بناءً على ما وصفته، قد تحتاج حالتك إلى رعاية طبية عاجلة. يُرجى طلب الرعاية الطارئة الآن: اتصل بالرقم **997** (الهلال الأحمر) أو **911** حيث يتوفر، أو توجّه إلى أقرب قسم طوارئ. لا تنتظر موعدًا مع طبيب مختص. هذا المساعد لا يستطيع تشخيص حالتك."

| القاعدة | الشرط | النتيجة |
|---|---|---|
| `RF_*` | الرسالة الخام تحتوي عبارة خطر (لا أستطيع التنفس، أُغمي علي، ألم شديد في الصدر، علامات جلطة دماغية) | **طوارئ**، والنموذج لا يُستدعى أبدًا |
| `E_PAIN_NOW` | ألم الصدر موجود الآن | **طوارئ** |
| `E_ASSOCIATED` | ألم صدر مع ضيق تنفس / إغماء / تعرق أو غثيان / ألم منتشر | **طوارئ** |
| `Q_PAIN_NOW` ← `Q_ASSOCIATED` ← `Q_ONSET` ← `Q_REVIEW` | المعلومة ما زالت مجهولة | اسأل عنها (فقط الأسئلة التي قد تغيّر المسار) |
| `U_RECENT` | بدأ اليوم وزال الآن، بدون أعراض | **عاجل**: زيارة طوارئ اليوم، وليس حجزًا |
| `S_REVIEW` / `S_REVIEW_OTHER` | تشخيص سابق للمراجعة | **رأي ثانٍ** |
| `S_CARDIOLOGY` | ألم قديم بدون أعراض | **طبيب مختص** (قلب) |
| `R_OTHER` | ليس ألم صدر ولا علامة خطر | **رعاية أولية** (طب أسرة) |

فحوص الطوارئ تعمل أولًا، فأي "نعم" لعلامة خطر تُنهي الأسئلة فورًا، وطلب الرأي الثاني لا يمكن أن يتجاوز حالة طوارئ. القواعد محافظة (تفضّل المبالغة في الحذر)، في ملف واحد، مختبرة باللغتين، و**موثقة كقواعد نموذج أولي وليست إرشادًا طبيًا**. النظام الحقيقي يحتاج قواعد يكتبها ويعتمدها أطباء.

**منع التشخيص مفروض بالكود** (`backend/app/no_diagnosis.py`): كل رد من النموذج يُفحص قبل أن يراه المريض. الرد الذي يذكر مرضًا (ذبحة، ارتجاع…) أو يخمّن سببًا ("يبدو أنه…") أو يقترح دواء ("خذ حبة…") أو يطمئن المريض كذبًا ("ليست حالة طارئة") يُحظر ويُستبدل برسالة ثابتة توجّهه للطبيب.

لماذا لا نثق بالنموذج هنا: ليس لأن النماذج أسوأ دائمًا في الفرز. النتائج المنشورة متباينة، ودراسة وجدت أن ChatGPT تعرّف على الحالات الخطرة أفضل من ممرضي الفرز ([JMIR 2024](https://doaj.org/article/3e9c85a398b543bab44f5293f804c800)). المشكلة هي **التكرار وقابلية التدقيق**: دراسة أخرى وجدت أن فرز ChatGPT ضعيف التكرار، بدقة 47.5% ونسبة تقليل من الخطورة 13.7% على مرضى محاكين ([Emergency Care Journal](https://www.pagepressjournals.org/ecj/article/download/15130/14090/101289)). قرار السلامة يجب أن يعطي نفس الإجابة في كل مرة وأن يُختبر سطرًا بسطر، و`if pain_now: EMERGENCY` كذلك.

## 6ب. الحجز: الموعد، التأكيد، التذكرة

المساعد يعمل كخدمة عملاء بعد القرار، لكن **الذكاء الاصطناعي لا يحجز أبدًا**: النموذج يطلب المواعيد لطبيب أُرجع في هذه المحادثة ← الواجهة تعرض مواعيد حقيقية ← المريض يضغط «تأكيد» ← الكود يتحقق (المحادثة موجودة، المسار قابل للحجز وليس طوارئ، هذا الموعد عُرض فعلًا في هذه المحادثة) ← معاملة واحدة في قاعدة البيانات (قفل الصف، التحقق أنه ما زال متاحًا، الحجز) ← **رقم تذكرة تولّده قاعدة البيانات**.

| الخطر | الحماية |
|---|---|
| حجز طبيب غير موجود في النظام | المواعيد لا تُجلب إلا لأطباء أرجعهم البحث، والتأكيد لا يقبل إلا مواعيد عُرضت |
| الذكاء الاصطناعي يحجز وحده أو يعلن حجزًا وهميًا | لا توجد أداة حجز للنموذج، وأي رد يقول "تم الحجز" أو يذكر تذكرة يُستبدل |
| اختراع رقم تذكرة | التذكرة من تسلسل Postgres، والرد قالب يُملأ من صف قاعدة البيانات |
| مريضان يحجزان نفس الموعد في نفس اللحظة | قفل صف + `UNIQUE(slot_id)`، ومختبر بخيطين متزامنين: واحد فقط ينجح |
| حجز أثناء طوارئ | مرفوض: جلسات الطوارئ مقفلة |

الحجز يرتبط بملف المريض **فقط إذا تحقق الاستقبال من هويته**، والزائر يحجز بدون ملف. المستشفى يستلم رقم الملف (مريضه)، ولا يستلم أبدًا التاريخ المرضي ولا أعراض اليوم.

### إشعار الطبيب والمستشفى (تجريبي من البداية للنهاية)

في **نفس المعاملة** التي يُحفظ فيها الحجز، يُكتب صفّان في صندوق الصادر (transactional outbox): **بريد للطبيب** و**رسالة لنظام المستشفى** بصيغة FHIR `Appointment`. بعد الحفظ، مُرسل تجريبي يعلّمهما كمُرسَلين، و`GET /api/v1/hospital/inbox` يُظهر ما استلمه الطبيب والمستشفى. الإشعارات تحتوي الوقت والمكان والتذكرة فقط، وليس أعراض المريض. ومختبر: الحجز الذي يفشل لا يُنتج أي إشعار.

لماذا صندوق الصادر: إذا تعطل البريد أو نظام المستشفى، يبقى الحجز محفوظًا ويُعاد إرسال الإشعار. لا يوجد حجز بدون إشعار، ولا إشعار لحجز فشل.

## 9. الأمان

**في النموذج الأولي:** تحقق من المدخلات على كل حدود النظام · استعلامات بمعاملات مربوطة فقط · الأسرار في متغيرات البيئة ومفتاح الذكاء الاصطناعي في الخادم فقط · CORS بقائمة مسموحة · قاعدة البيانات لا يُوصل إليها إلا عبر الخادم · التحقق من هوية المريض بالملف أو الهوية **مع تاريخ الميلاد**، برسالة فشل موحّدة، وحد 3 محاولات، وحذف المعرّفات بعد التحقق · صلاحيات الأدوات حسب المسار · حد معدّل الطلبات على `/chat` · السجلات تحتوي أنواع الأحداث والمعرّفات وليس نص الأعراض.

**مطلوب قبل الإنتاج (غير منفّذ هنا):** مصادقة وموافقة المريض، تشفير البيانات المخزنة، سجل تدقيق، مراجعة موقع تخزين البيانات (نظام حماية البيانات الشخصية PDPL وضوابط الهيئة الوطنية للأمن السيبراني)، **تقييم تنظيمي من هيئة الغذاء والدواء (SFDA)**، لأن البرمجيات التي توجّه القرارات السريرية قد تُعتبر جهازًا طبيًا حسب [SFDA MDS-G010](https://www.sfda.gov.sa/en/guide/guidance-artificial-intelligence-and-machine-learning-aiml-enabled-medical-devices-mds-%E2%80%93-g010)، وقواعد فرز معتمدة من أطباء، واتفاقيات معالجة بيانات مع مزوّد النموذج، واختبار اختراق، ومراقبة. **هذا النموذج الأولي لا يدّعي أي توافق تنظيمي.**

## 10. معالجة الأخطاء

شكل خطأ موحّد في كل مكان: `{"error": {"code", "message", "request_id?"}}`. لا تصل تفاصيل الأخطاء البرمجية ولا SQL للمستخدم أبدًا.

| العطل | السلوك |
|---|---|
| مدخلات غير صالحة | `422` قبل أي استعلام |
| طبيب أو مستشفى غير موجود | `404` |
| قاعدة البيانات متعطلة | `503`، والمحادثة تقول إنها لا تستطيع الوصول ولا تخترع شيئًا |
| خدمة الذكاء الاصطناعي متعطلة | محاولة واحدة إضافية، ثم *"خدمة الذكاء الاصطناعي غير متاحة مؤقتًا… إذا كنت تشعر بتوعك الآن اتصل بالرقم 997"*، وفحص العلامات الحمراء يستمر في العمل |
| لا يوجد مقدم خدمة مطابق | رسالة صريحة، حتى لو ادّعى النموذج غير ذلك |
| طوارئ | يتوقف البحث عن مقدمي الخدمة، ورسالة طوارئ ثابتة |

## 11. الافتراضات

- لم تُقدَّم بنية أو بيانات أو قواعد سريرية حقيقية من HealTrip، لذا فمقدمو الخدمة والأسعار والمواعيد والمرضى خياليون.
- أرقام الطوارئ سعودية (997 للإسعاف، و911 الموحّد في الرياض ومكة والمدينة والشرقية) لأن HealTrip مسجلة في السعودية.
- قواعد الفرز توضيحية ومحافظة، كتبها مهندس وليس طبيبًا.
- "الرأي الثاني" يعني مريضًا لديه تشخيص أو خطة علاج ويريد مراجعتها، غالبًا عن بُعد قبل السفر.

## 12. التطور المستقبلي

- **تقوية الحجز**: حجز مؤقت للموعد أثناء تفكير المريض، وتأكيد آمن عند التكرار، والإلغاء وإعادة الجدولة.
- **خط سير الحالات في CRM** مع سجل تدقيق لكل جولة وكل أداة، و**قائمة مراجعة بشرية** للحالات عالية الخطورة أو غير الواضحة.
- **RAG** للمعرفة غير المنظمة (الإجراءات، السفر والتأشيرات، التأمين) مع الاستشهاد بالمصادر والرفض عند عدم وجود مصدر.
- واجهة API لانضمام المستشفيات الشريكة، وربط المواعيد الحقيقية.
- مجموعة تقييم: سيناريوهات مرضى ثابتة بالعربية والإنجليزية تُشغَّل مع كل تغيير في التعليمات أو النموذج.
- مراقبة: مسار كل جولة، والتكلفة والزمن لكل محادثة.

### طبقة الإيرادات: الترقية والبيع المتقاطع (نسخة مصغّرة منفّذة)

HealTrip عمل في السياحة العلاجية، فمسار القرار هو أيضًا مكان الإيرادات. القاعدة: **البيع لا يلمس القرار الطبي أبدًا.**

- مسار الرعاية يُحسب **قبل أي عرض وبشكل مستقل عنه**، وكود الفرز لا يرى الأسعار ولا الشركاء.
- **لا عروض في مسارات الطوارئ أو العاجل.** خطوة العروض لا تُستدعى أصلًا.
- العروض تأتي من جدول `offers` مثل الأطباء، فالنموذج لا يستطيع اختراع باقة أو سعر، ولا يستلم العروض أصلًا: الواجهة تعرضها من صفوف قاعدة البيانات.
- تظهر فقط **بعد أن يؤكد المريض** ملخص مساعد العيادة، وعروض السفر تظهر فقط إذا كان الطبيب المطابق خارج البلد.

| مسار الرعاية | بيع متقاطع (خدمة مرتبطة) | ترقية (مستوى أعلى) |
|---|---|---|
| رأي ثانٍ | مراجعة الملفات عن بُعد قبل السفر، وترجمة التقارير الطبية | مراجعة بأولوية، واستشاري أول |
| طبيب مختص في الخارج | التأشيرة، فندق قرب المستشفى، التوصيل من المطار، مترجم | خدمة كبار الشخصيات: توصيل خاص، سكن للمرافق، منسق خاص |
| طبيب مختص / رعاية أولية | باقة فحص في المستشفى المطابق (مثل فحص القلب) | فحص تنفيذي شامل |
| وجود تاريخ عائلي | فحص العائلة عبر **شجرة الصحة** في HealTrip | — |
| بعد العلاج | متابعة عن بُعد، وباقة تأهيل | خطة متابعة ممتدة |

## التشغيل محليًا

</div>

```bash
docker compose up -d                       # Postgres 16 + pgvector on :5433
cd backend
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env
.venv/bin/python -m app.seed --reset       # schema + mock data
.venv/bin/uvicorn app.main:app --port 8000
.venv/bin/python -m pytest -q              # 87 tests, separate healtrip_test DB

# frontend (second terminal)
cd frontend && npm install && npm run build && npx next start -p 3100   # http://localhost:3100
```
