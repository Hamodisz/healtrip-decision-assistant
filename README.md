# HealTrip — AI Patient Decision Assistant (Prototype)

A **Decision-First** AI assistant for HealTrip: the system first reaches an accurate, explainable, evidence-backed medical-routing decision (**ER, specialist, second opinion, or primary care**), and only then acts on it: matching a real doctor from the network, booking a real slot, and issuing a ticket number.

> Decision first, booking second. The decision is the product; the booking is its consequence.

> **Demo chat:** _coming soon (link will be added when the chat UI milestone ships)_
> **Status:** 🚧 In progress. See [Roadmap](#roadmap). This README is updated as each milestone lands.

> ⚠️ Prototype with **mock data only**. Not medical advice. All doctors, hospitals and slots are fictional.

---

## The core problem this prototype is designed around

A patient types:

> *"I have chest pain and I'm not sure whether I should see a cardiologist, go to the ER, or seek a second opinion."*

An LLM on its own will answer this fluently, and that is the risk. It can:
1. **Under-triage an emergency** (chest pain can be a heart attack)
2. **Invent doctors, hospitals, time slots, or ticket numbers** that don't exist
3. **Take a real-world action** (a booking) the patient never agreed to

So the design principle is:

> **The model reasons and talks. Code decides what is true and what is allowed. Humans approve what is high-risk.**

## Conversation flow (Decision-First)

```
Patient message (Arabic or English)
     │
     ▼
┌─────────────────────┐  red flag (AR/EN rules)  ┌─────────────────────────────────┐
│ 1. HealTrip SOS     │ ───────────────────────▶ │ Fixed emergency response, local │
│    gate (code only) │                          │ emergency number, case flagged. │
└─────────────────────┘                          │ Flow ends. No AI involved.      │
     │ safe                                      └─────────────────────────────────┘
     ▼
┌─────────────────────┐
│ 2. ASK              │  clarifying questions until a structured `triage` object is complete
└─────────────────────┘
     ▼
┌─────────────────────┐
│ 3. DECIDE           │  Decision Record: decision + reasons (each tied to a patient fact)
│                     │  + confidence + "what would change this decision"
└─────────────────────┘
     ▼
┌─────────────────────┐
│ 4. VERIFY           │  grounding verifier: every ID came from a tool call this turn,
│                     │  every reason cites something the patient actually said
└─────────────────────┘
     ▼
┌─────────────────────┐  high-risk / low-confidence  ┌──────────────────────────────┐
│ 5. GOVERN           │ ───────────────────────────▶ │ Human review queue (CRM).    │
│                     │                              │ Clinician/coordinator decides│
└─────────────────────┘                              └──────────────────────────────┘
     │ approved
     ▼
┌─────────────────────┐
│ 6. ASSIGN + BOOK    │  search_doctors → get_available_slots → hold → patient confirms
└─────────────────────┘
     ▼
┌─────────────────────┐
│ 7. TICKET           │  ticket number generated by the DATABASE, e.g. HT-2026-000123
└─────────────────────┘
```

Stages are enforced as a **state machine in code**, not just described in the prompt. Booking is unreachable until an approved decision exists, and every stage transition is written to an audit log.

## Planned architecture

```
┌─────────────────────┐      HTTPS/JSON      ┌──────────────────────────────────────────┐
│  Next.js chat UI    │ ───────────────────▶ │  FastAPI (Python, async)                 │
│  AR (RTL) / EN (LTR)│ ◀─────────────────── │                                          │
└─────────────────────┘                      │  /chat router                            │
                                             │    └─ SOS gate (rules, no AI)            │
                                             │    └─ Decision agent (LLM + tool loop)   │
                                             │         ├─ Tools (read: doctors, slots,  │
                                             │         │   knowledge; write: hold_slot) │
                                             │         └─ Grounding verifier            │
                                             │  Governance (review queue, audit log)    │
                                             │  Booking service (transactions, tickets) │
                                             │  Repository layer (shared by API+tools)  │
                                             └──────────────┬───────────────────────────┘
                                                            │ SQLAlchemy (parameterized)
                                                            ▼
                                             ┌──────────────────────────────────────────┐
                                             │  PostgreSQL + pgvector                   │
                                             │  doctors · hospitals · slots · bookings  │
                                             │  patient_cases · decisions · case_events │
                                             │  knowledge_chunks (RAG)                  │
                                             └──────────────────────────────────────────┘
```

| Layer | Choice | Why |
|---|---|---|
| Frontend | Next.js | Simple chat, easy RTL/LTR switching |
| Backend | FastAPI (Python) | Async, typed (Pydantic) request/response contracts, auto OpenAPI docs; strongest AI/RAG ecosystem |
| DB | PostgreSQL + SQLAlchemy | Relational data (doctors ↔ slots ↔ bookings) + transactions for booking |
| Vector search | pgvector | RAG in the same DB, no extra infrastructure for a prototype |
| AI | LLM with native tool calling | Tools return real data; the model never writes SQL |

### Database structure (M1 ✅)

```
specialties                hospitals                         doctors
───────────                ─────────                         ───────
code  PK ("cardiology")    id  PK ("HOSP-001")               id  PK ("DOC-001")
name_en                    name_en / name_ar                 name_en / name_ar
name_ar                    country (ISO-2) · city            specialty_code  FK → specialties
                           timezone (IANA)                   hospital_id     FK → hospitals
                           has_emergency                     languages[]
                           accreditation                     years_experience
                           languages[]                       offers_second_opinion
                           is_mock                           offers_remote_consult
                                                             consultation_fee · currency
                                                             is_mock
slots
─────
id PK · doctor_id FK → doctors · starts_at (timestamptz) · duration_min
mode (in_person | remote) · status (open | held | booked) · held_until
UNIQUE (doctor_id, starts_at)  ·  CHECK status/mode  ·  INDEX (doctor_id, status, starts_at)
```

Decisions behind the schema:
- **Readable IDs** (`DOC-001`, `HOSP-001`): the AI may only reference a provider by an ID a tool returned. Readable IDs make that rule easy to audit in logs and tests.
- **Cross-border by design**: `country`, `timezone`, `languages`, `currency`, `offers_remote_consult`. A patient in Riyadh can get a remote second opinion from Berlin before deciding to travel.
- **Slots in local time**: generated on each country's working days (KSA Fri/Sat weekend) and stored as `timestamptz`.
- **ER is not bookable**: emergency-medicine doctors have no slots. An ER decision resolves to hospitals with `has_emergency = true`, never to an appointment.
- **Holds expire by query**: a `held` slot whose `held_until` has passed is offered again. No cron job is needed to release abandoned holds.
- **Constraints in the DB, not just the app**: unique (doctor, time) and CHECK constraints protect data even if application code has a bug.

Mock network: 6 hospitals (Riyadh, Jeddah, Dubai, Istanbul, Berlin), 15 doctors across 9 specialties, ~760 slots over 14 days. **All fictional**: every row has `is_mock = true` and hospital names start with "Demo".

### API (M1 ✅)

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/health` | Liveness + DB check |
| GET | `/api/v1/specialties` | Specialty codes (AR/EN names) |
| GET | `/api/v1/hospitals?country=&city=&has_emergency=` | Hospital search |
| GET | `/api/v1/doctors?specialty=&country=&city=&language=&second_opinion=&remote_consult=` | Doctor search |
| GET | `/api/v1/doctors/{id}` | One doctor with hospital + specialty |
| GET | `/api/v1/doctors/{id}/slots?days=&mode=` | Open slots (next 1–30 days) |

Interactive docs: `http://localhost:8000/docs` (OpenAPI, generated by FastAPI).

**One repository layer** (`backend/app/repository.py`) holds every provider query. The REST API and the AI agent's tools (M3) both call it, so the model can never see data the API wouldn't return, and there's one set of queries to secure. All inputs are validated at the boundary (strict patterns, ranges, result cap of 20) before any query runs.

**Error contract:** every error has the same shape `{"error": {"code", "message", "request_id?"}}`. Stack traces and SQL never reach the client; they are logged server-side under the `request_id`.

## How hallucination is prevented (by design, not by prompt)

| Risk | Guard |
|---|---|
| Invented doctor / hospital | Model may reference providers **only by ID** returned by a tool call in the same turn. Backend rejects unknown IDs → regenerate once → deterministic fallback. |
| Invented doctor details | Provider cards in the UI are rendered **from DB rows**, never from model text. |
| Invented slot / ticket number | Slots come only from `get_available_slots`; ticket number is generated by the DB and rendered from the booking row. |
| Invented medical/policy facts | RAG answers must cite chunk IDs that were actually retrieved; no relevant chunk → *"I don't have that information."* |
| Missed emergency | HealTrip SOS: bilingual red-flag rules run **before** the model is called. |
| Unexplainable decision | Every decision carries reasons tied to patient facts, a confidence and an audit trail; high-risk decisions need human approval. |
| Booking without consent | AI can only *hold* a slot; booking needs explicit patient confirmation checked in code. |
